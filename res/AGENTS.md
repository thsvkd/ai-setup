## 원칙

1. **이해 후 변경**: 기존 구현·테스트·문서를 먼저 읽은 후 변경한다. 불명확한 것과, 숨겨진 가정을 조용히 선택하지 말고 개발자와 논의. 더 단순한 접근이 있으면 드러내고, 근거가 있으면 요청받은 방식에 반대한다.
2. **최소 변경**: 근본 원인을 해결하는 범위 안에서 최소한만 바꾼다. 증상만 덮는 우회도, 요청하지 않은 기능·추상화·스타일 개선도 넣지 않는다. 근본 원인이 요청 범위를 벗어나면 확장하지 말고 먼저 논의한다.
3. **목표 주도 실행**: 작업을 검증 가능한 성공 기준으로 바꾸고, 다단계 작업은 `단계 -> 검증` 계획을 먼저 말한다. 합의된 기준 — 사용자가 명시했거나 `docs/TEST_SPEC.md`에 있는 것 — 이 있으면 되묻지 않고 통과할 때까지 반복한다. 스스로 세운 기준은 확인 전까지 합의가 아니다.
4. **증거 기반 완료**: 실측으로 검증하지 않고 완료했다고 말하지 않는다. 통과·실패·건너뜀·미검증을 구분해 보고한다.

> 저위험(되돌릴 수 있고 공개 API·데이터·보안에 영향 없음)·소규모 작업에는 가볍게 적용한다. **이 완화는 Don't 에 적용되지 않는다.**

### SSoT 계층 (SSoT 태그가 붙은 문서)

- `docs/PRD.md` — 목표, 기능, 요구사항 명세.
- `docs/SPEC.md` — 어떻게 만드는가. 자주 바뀌지 않는 계약을 구현을 복원할 수 있는 수준으로.
- `docs/TEST_SPEC.md` — 무엇이 완료인가. 사용자와 합의한 수용 케이스 목록의 유일한 SSoT.
  - 테스트 케이스는 `WHEN <조건> THE SYSTEM SHALL <기대 동작>` 형식으로 쓴다. 조건절이 그대로 테스트 이름이 된다.
  - 테스트 통과는 완료의 필요조건이지 충분조건이 아니다. 일반해 구현을 해야하며, 테스트만 노린 특수 구현은 미완료다.
  - 여기 없는 케이스는 완료 범위 밖이다. 공백을 발견하면 채우지 말고 목록에 넣을지 먼저 합의한다.

> 구현과 설명 문서가 SSoT와 충돌하면 SSoT가 기준이다. SSoT끼리 충돌하거나 사용자의 명시적 지시와 충돌하면 조정하지 말고 중단하고 보고한다. SSoT 수정은 사용자 승인하에서만 한다.

## 규칙

### Do

- 작업 완료시 문서 동기화 진행.

### Don't

- 테스트를 약화·삭제·skip 하거나 단언을 느슨하게 만들어 통과를 만들지 않는다.
- 시크릿을 출력·로그·하드코딩·커밋하지 않는다. 환경 변수나 시크릿 매니저 경로로 참조하고, 노출을 발견하면 즉시 보고한다.

> 위 항목은 훅·권한·CI 로도 차단돼 있을 수 있다. 차단에 걸리면 우회하지 말고 보고한다.

## 오케스트레이션

- 작업의 난이도에 따라 다음과 같이 진행
  - 쉬움: 주 에이전트가 끝까지 작업을 완료.
  - 중간: 주 에이전트가 끝까지 책임지되, 독립적이고 큰 작업은 서브에이전트에 위임한다. 적절한 모델을 선택.
  - 어려움: 모델라우팅 + 워크플로 방식으로 진행.
- 작성과 검토는 다른 컨텍스트에서 한다. 자기 코드를 자기가 승인하지 않고, 검토자는 작성자와 같거나 더 높은 등급의 모델로 한다.

- 완료의 증거를 제시할 것.
- 보고시 항목에 ID를 부여 명확한 의사소통이 되도록 할 것.
- `docs/REPORTING.md`에 따라 현대적인 HTML 보고서를 작성.
