## 개요

## 원칙

1. **이해 후 변경**: 기존 구현·테스트·문서를 먼저 읽는다. 가정은 명시하고, 해석이 둘 이상이면 조용히 고르지 말고 논의한다. 막히면 멈추고 무엇이 불명확한지 이름 붙여 묻는다. 더 단순한 접근이 있으면 말하고, 정당한 근거가 있으면 요청받은 방식에 반대한다.
2. **최소 변경**: 요청한 지시에 대해 최소한의 변경만 가한다. 기존 내용을 "개선"하지 않고 기존 스타일을 따른다. 요청하지 않은 기능·추상화·설정 가능성은 넣지 않는다. 자가 점검: 바뀐 모든 줄이 요청으로 곧장 추적되는가, 시니어 엔지니어가 과설계라고 할 만한가.
3. **목표 주도 실행**: 작업을 검증 가능한 성공 기준으로 바꾼다. 다단계 작업은 `단계 -> 검증` 형태의 짧은 계획을 먼저 말한다. 기준이 강하면 되묻지 않고 검증될 때까지 스스로 반복한다.
4. **증거 기반 완료**: 실행하지 않은 검증을 통과했다고 말하지 않는다. 통과·실패·건너뜀·미검증을 각각 구분해 보고한다.

> 저위험·소규모 작업에는 이 원칙을 가볍게 적용한다. 비가역성·보안·호환성·공개 API 영향이 커질수록 계획·테스트·리뷰 강도를 올린다.

### SSoT 계층 (SSoT 태그가 붙은 문서)

- `docs/PRD.md` — 무엇(What)을, 왜(Why) 만드는지. 목표·비목표와 성공 지표. 기계적 완료 판정은 여기가 아니라 `docs/TEST_SPEC.md`가 한다.
- `docs/SPEC.md` — 어떻게(How) 구현할 것인가를 명세. 자주 바뀌지 않는 계약(공개 인터페이스·데이터 형식·호환 규칙)을 구현을 복원할 수 있는 수준으로 쓴다. 변경 단위의 상세 명세는 `docs/handoffs/`가 맡는다.
- `docs/TEST_SPEC.md` — 무엇이 완료인가를 정의. 인간이 합의한 테스트 케이스 목록이자 코드베이스 무결성의 목표함수이며, 수용 기준의 유일한 SSoT다.
  - 케이스는 `WHEN <조건> THE SYSTEM SHALL <기대 동작>` 형식으로 쓴다. 조건절이 그대로 테스트 이름이 되고, 모호성·누락·모순을 기계적으로 검사할 수 있다.
  - 테스트 코드는 `docs/TEST_SPEC.md`를 1:1로 컴파일한 수준으로 작성되어야 함.
- `docs/handoffs/<작업>.md` — 이번 변경을 어떤 순서로 하는가. 합의된 케이스·핵심 결정·기각한 대안·관련 코드 포인터. 작업 단위로 만들고 완료 후에도 기록으로 남는다.

> 구현과 설명 문서가 SSoT와 충돌하면 SSoT가 기준이 된다.
> 사용자의 명시적 지시가 SSoT와 충돌하면 임의로 한쪽을 따르지 말고 차이를 먼저 보고한다.
> SSoT는 구현을 복원할 수 있는 수준으로 작성한다.
> SSoT를 수정하는 것은 인간의 승인하에서 이루어진다.

## 규칙

### Do

- 되돌릴 수 있는 로컬 작업은 스스로 진행한다. 되돌리기 어렵거나 저장소 밖에 영향을 주는 작업은 먼저 확인받는다.
- 설명·검토·진단 요청에는 읽기와 비파괴 검증까지만 한다. 변경 요청에는 범위 안의 편집과 그에 필요한 검증이 포함된다.
- 한 작업에서 받은 승인을 다른 작업에 재사용하지 않는다.

### Don't

- 테스트를 약화·삭제·skip 하거나 단언을 느슨하게 만들어 통과를 만들지 않는다.
- 사용자 승인 없이 `git push`, 릴리스, 외부 시스템 쓰기, 과금·권한 변경을 하지 않는다.
- 시크릿을 출력·로그·하드코딩·커밋하지 않는다.

## 오케스트레이션

- 기본은 주 에이전트 한 명이 끝까지 책임지는 것이다. 서브에이전트는 (1) 작업이 실제로 독립적이고 (2) 경계가 명확하며 (3) 요약 결과만 받아도 충분할 때만 쓴다.
- 주 에이전트가 범위·충돌 방지·통합·최종 검증을 소유한다. 서브에이전트 보고를 검증 없이 완료 근거로 삼지 않는다.
- 작성과 검토는 다른 컨텍스트에서 한다. 같은 대화 안에서 자기 코드를 승인하지 않는다.
- 병렬 실행은 서로 다른 파일을 만질 때만 한다. 같은 파일을 여러 에이전트가 동시에 편집하지 않는다.
- 모델은 역할 등급으로 고른다 — 단순 조회·기계적 변환은 소형, 일반 구현은 중형, 아키텍처·보안·근본 원인 분석은 대형. 모델 ID 는 자주 바뀌므로 이 파일에 고정하지 않는다. 저장소 기본값은 `docs/ORCHESTRATION.md`.
- 긴 작업은 결정과 증거를 `docs/handoffs/`에 남긴다. 인계 수단은 대화 컨텍스트가 아니라 문서다.
