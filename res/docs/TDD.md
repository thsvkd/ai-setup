# TDD

## 루프

`RED -> GREEN -> 리팩터`. 각 단계를 건너뛰지 않는다.

- **RED**: 새 테스트가 실패하는 것을 눈으로 본다. 한 번도 실패한 적 없는 테스트는 아무것도 검증하지 않는다.
- **GREEN**: 스위트 전체가 통과. 러너가 없어 건너뛴 스위트는 통과가 아니다.
- **리팩터**: 테스트를 그대로 둔 채 구현만 정리한다. 둘을 같이 바꾸면 어느 쪽이 깨졌는지 알 수 없다.

## 테스트 작성

- 케이스 하나에 테스트 하나. 이름은 `TEST_SPEC.md`의 조건절을 그대로 쓴다.
- 각 테스트에 `covers: Test-N` 을 남겨 케이스와 연결한다.
- 구현의 내부 단계가 아니라 계약(입력 -> 관찰 가능한 결과)을 검증한다.
- 실제 사용자 홈·시크릿·에디터 설정을 대상으로 삼지 않는다. 임시 디렉터리를 쓴다.

## 실패했을 때

- 테스트를 고치기 전에 "테스트가 옳은가"를 먼저 판정한다. 대개는 구현이 틀렸다.
- 약화·삭제·skip·단언 완화로 통과를 만들지 않는다. 통과시키지 못하면 실패 그대로 원인을 보고한다.
- 같은 가설로 진전 없이 3회 실패하면 멈추고 실패 로그와 함께 보고한다.

## 적대적 리뷰

작성자와 다른 컨텍스트에서, 작성자와 같거나 더 높은 등급의 모델로 돌린다.

- **뮤테이션 점검**: 구현을 일부러 깨뜨려 해당 테스트가 RED 가 되는지 확인한다. 그대로 통과하면 그 테스트는 비어 있다.
- 심각도: `CRITICAL`(데이터 손실·보안) / `HIGH`(계약 위반·오동작) / `MEDIUM`(누락된 케이스) / `LOW`(가독성).
- `CRITICAL`·`HIGH` 는 고치기 전에는 완료가 아니다. 나머지는 기록하고 사용자가 판단한다.
